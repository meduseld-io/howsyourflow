#Overview

current is a board for the working day. It reads your Jira tickets and your GitHub pull requests, works out which of them have a next action, and puts those in front of you in the order they need you.

It runs on your own machine, reads your own accounts and sends nothing anywhere. There are no dependencies, no build step and no account to create.

It is deliberately not a list of everything you own. A list of every open item is a second backlog, so anything that trips none of the signal rules stays quiet.

#Quick start

You need Node 18 or later. Nothing else is installed.

The repository is internal to Upwind. Ask in engineering for the address. Its README carries the setup that is specific to Upwind, which is the part this page leaves out. 

$ git clone <the Upwind repository>
$ cd <the repo>/current
$ npm run setup

The walkthrough checks Node, creates your .env, reports which sources are connected, offers to sign you in to GitHub, reads your calendar, and is honest about the one step it cannot do for you. It asks before anything with a side effect and is safe to re-run. Pass -- --check to see what it would do without it doing anything.

On a Mac the last step offers to build the app, which is the way to run this. It sits in your dock, starts the board itself and can tell you a meeting is about to start with its window shut. A browser tab is the first thing you close. 

$ open ~/Applications/current.app

Or keep it in a tab instead.

$ npm start

Then open http://localhost:4319.

The board starts with nothing configured and tells you what is missing. Settings holds a Check setup panel that names each source, says whether it is working, and gives you the exact command to fix it. It opens by itself only when something is genuinely broken.

You can stop here. With GitHub connected and Jira left alone, the board runs GitHub-only. Every source below is optional.

#Connecting GitHub

Either route works, and you only need one.

#The gh CLI

$ gh auth login

That is it. The board reads the token from the gh CLI, so if gh auth status works, so does this. No secret is stored anywhere.

#A personal access token

If gh is not installed or not an option on your machine, put a personal access token with the repo scope in .env instead. Notifications need nothing beyond it. 

$ cp .env.example .env
$ echo "GITHUB_TOKEN=ghp_..." >> .env

GITHUB_TOKEN wins over the CLI, which is also how you point the board at a different account from the one gh is signed in to.

#Connecting Jira

One command, the same bargain as GitHub. The session is yours, so the board shows your tickets and nothing is stored in a file. 

$ acli jira auth login --web

That opens a browser once. Afterwards acli jira auth status answers for the board, exactly as gh auth status does for GitHub.

No JIRA_ASSIGNEE, and no token variables. A provisioned token belongs to whoever created it, so currentUser() meant them rather than you, and the board would authenticate perfectly and report that you had no tickets. Signed in as yourself that cannot happen, and the setting that used to work around it is gone.

#Why it fills in twice

Worth knowing, because you will see it. acli jira workitem search returns eight fields and updated, duedate, parent, resolutiondate and comment are not among them. There is no room for them in its response type, so no flag reaches them and *all is refused as well. Those come from acli jira workitem view, one ticket per call.

So the board draws itself from the search straight away and fills the detail in behind, six at a time, cached for ten minutes. A cold start shows the whole list at once, and timestamps, epic grouping and comments arrive a few seconds later rather than holding the page up.

#When the session expires

It will. acli sessions run out, usually overnight, and a board that was right yesterday opens today with Jira answering nothing. That used to look exactly like a day with no tickets on it, which is the one reading that is both plausible and wrong.

So a signed-out Jira says so, and offers a Sign in button in the banner and in the Setup panel. It opens the same browser tab the command does and takes about as long as approving it. Not signed in and not signing in, Jira is simply absent and the board runs GitHub-only.

#Calendar

With a calendar configured, a strip above the board says how much of the day is already spoken for and how long the largest uninterrupted block is, which is the number that actually changes a decision. Three hours clear means picking up a review; forty minutes between two meetings does not.

#From macOS Calendar

$ node scripts/sync-calendar.mjs

This asks Calendar.app for today's meetings and writes the snapshot. It needs no OAuth client, no app registration and no administrator, only the one-time automation prompt macOS shows on first run. It deduplicates, so a meeting held in both a work calendar and a subscribed copy appears once.

You should not have to run it. A snapshot only describes the moment it was taken, and a step you must remember every morning is a step that does not happen, so one older than ten minutes is refreshed in the background. CALENDAR_AUTOSYNC=off turns that off.

#Meetings that move or vanish

Each sync is compared against the one before it. A meeting whose title is still in the day at a different time is marked where it now sits rather than listed twice. One that has gone from the calendar entirely is put back in its old slot, greyed, saying it was taken out, because a meeting silently disappearing from your morning is the change you are most likely to miss. Neither is counted in the day's totals: a cancelled hour is free.

Both are matched on the title, which is the only stable thing a snapshot carries. That makes the match ambiguous the moment a title appears twice, and recurring one-to-ones genuinely do appear several times in a day, so a title that is not unique on both sides is left alone and only the disappearance is reported. A move is claimed only where there is exactly one candidate it could be.

#From an iCal address

Set CALENDAR_ICS_URL to a calendar's private iCal address. In Google Calendar that is Settings › your calendar › "Secret address in iCal format".

Treat the secret address as a password. It grants read access to that calendar. A Workspace administrator can remove it, leaving only a public address that would publish your calendar to anyone holding the URL. Never use the public one. Where the secret address is gone, the macOS route above is the way in.

Failing both, data/calendar-snapshot.json is read instead, holding either raw events or an already-summarised day; lib/calendar.js documents both shapes. With none of the three, the strip simply does not appear.

Only daily and weekly recurrence is expanded. Standups, one-to-ones and team meetings are almost all one or the other, and a full RRULE implementation buys very little for a working day. Meetings you declined, and meetings where everyone else declined, are left out.

The top of the page answers "what now", split into groups because they are different kinds of obligation.

Above them, a calendar strip gives the shape of the day, and a standup summary collects what you finished, what you are on and what is blocking you since the last working day, colour coded by state and copyable as plain text.

An item that trips several rules appears once, led by its most urgent reason. Click a headline count to dim the page to just those items, and press / to search by ticket key, pull request number or title.

#Signal reference

These rules decide what is worth raising. They are grouped here by colour, in the same severity order the board itself ranks them in.

Any of them can be switched off under Signals in settings, with a count beside each one of how much it is raising today. Switching one off takes away a reason rather than a card: a pull request that is both red and waiting on review still wants reviewing once CI failing is off, so the next reason takes over and the rest fall in behind it. Only work with nothing left to say about it goes.

#Linking tickets and PRs

Ticket keys such as PROJ-1234 are read out of pull request titles and branch names and joined to your Jira issues, so a ticket row shows its pull requests and a PR row shows its ticket. That linking is what powers the out-of-sync checks.

A ticket key ending in -0, such as PROJ-0, is read as a placeholder for "no ticket" and is linked to nothing. That rule is built in and needs no configuration.

#Jira statuses

Two of the rules match on the name of a Jira status rather than its category, because Jira's categories cannot tell "in review" apart from any other work in progress. Teams name these differently, so both are configurable.

SettingDefault
JIRA_REVIEW_STATUSES code review, in code review, in review, review, reviewing, peer review
JIRA_PARKED_STATUSES on-hold, on hold, blocked, paused, parked, deferred

The setup panel names statuses it does not recognise. If none of your in-progress statuses reads as review, the Ticket out of sync rule can never fire, and an absent nudge looks exactly like having nothing to be nudged about. The Jira statuses check reports what it found and what each status was taken to mean, so a name the rules do not know is visible rather than inferred from a section that never appears.

#Filters and per-viewer state

Everything in this section is yours alone. It is stored in localStorage in your browser, never sent to the server and never shared.

A # reference in a note links to the thing it names: #ABC-123 for a ticket, #42 for a pull request. Clicking one runs the same highlight the search box uses, because what is being pointed at is usually in the other column.

#Merging

A Ready to merge label is also the merge button. Two clicks: the first arms it, the second merges.

The server re-checks the preconditions against GitHub at the moment of merging rather than trusting the browser, and reads each repository's allowed merge method rather than assuming one.

#Desktop notifications

Off until you ask for it. Settings › Notifications › Enable asks the browser for permission, after which the board can tap you on the shoulder when something needs you. Two categories, each switchable on its own:

CategoryRaised for
Review asked of youSomeone is blocked until you look
Your PR changed stateReady to merge, changes requested, CI failing or merge conflicts

What is raised comes from the same focus rules the board itself uses, so a notification can never tell you something the board disagrees with. Several at once arrive as a single notification counting them, rather than one popup each, and nothing is raised while you are actually looking at the board.

They arrive only while a board tab is open, though it can be a background tab. Raising them with the board closed would need the Push API, which routes through a third-party push service, and sending your work queue to someone else's server is the one thing this project does not do.

If you ever press Block, the browser will not ask again. The only way back is to allow notifications for the site in your browser's own settings. The panel says so rather than showing a button that cannot work.

Nothing is sent anywhere: these are raised by the page itself. The permission is the browser's, and the switches, categories and the record of what has already been announced are stored per-viewer in localStorage.

#Search, the tour and the game

#Search

The box in the header filters the board by ticket key, pull request number or title, dimming everything that does not match and outlining what does, the same treatment the headline counts use, since they answer the same question. Press / to focus it and Escape to clear.

Keys and numbers get written inconsistently, so matching also compares with every non-alphanumeric character stripped: ABC-123, abc123 and 123 all find the same ticket, and 342 finds #342.

#The guided tour

The ? button in the header runs a guided tour: it freezes the page, spotlights each section in turn and explains what it is for. The steps are declared at the top of public/tour.js, anchored to data-tour attributes, and any step whose target is not on the page is skipped. Most sections remove themselves when empty, and stopping on a blank rectangle would be worse than moving on.

#The loading strip

While the board loads, the strip under the header shows an entry from Wikipedia's "on this day". Those picks lean heavily on wars, disasters and killings, because that is what tends to be historically notable, which is a poor fit for something glanced at during standup. lib/facts.js filters that subject matter out and tops the pool back up from the longer events feed for the same day when filtering leaves too little. The matching errs towards discarding: there are far more entries per day than the buffer needs, so a false positive costs nothing.

#Surfing

A small surfing game, in the spirit of Chrome's offline dinosaur. It is offered while the first fetch runs, under the error if that fetch fails, and from Settings at any time. Space or tap to jump, hold for height, down to duck under a low gull.

It opens over the board rather than inside it, so a re-render cannot destroy a run. A refresh that finishes while the game is open is held rather than applied: the frame says the board has updated, and shows it when you are ready. Closing the game applies whatever was waiting.

#Service status dots

The dots in the header show the public status pages for GitHub, Jira, Rovo, Claude and Slack. They exist because a degraded upstream makes this board look broken: when GitHub is struggling the review queue quietly goes stale, so anything not operational is named on the button rather than hidden behind a click.

No credentials are involved; these are public endpoints. Which services appear is chosen in Settings, and anything running Statuspage can be added by pasting the address of its status page. A page that is not a Statuspage site is rejected when you add it, rather than sitting in the header as a permanent grey dot.

The server is what fetches these, so a URL naming a private or loopback address is refused: a settings field should not become a way of reaching things inside the network the server sits in. A status page that cannot be reached is shown as unknown rather than as an outage.

#The team view

The board answers "what should I pick up". There are three questions it cannot answer by looking at any one person: who is stuck, who is carrying how much, and which of the team's own pull requests are sitting unreviewed. Those are a different view, and a toggle at the bottom of settings swaps to it.

It is off until a team exists. Set TEAM in .env, one entry per person, pairing their Jira address with their GitHub handle: 

TEAM=ada@example.com:ada-l, grace@example.com:ghopper:Grace H

The mapping has to be written down because nothing either side returns connects the two: Jira knows people by work email and GitHub by handle. A third field names anyone whose display name is not their address, though it is rarely needed, since Jira's own spelling of a name wins over the one read out of an email. Without a TEAM the toggle does not appear at all.

A handle GitHub has never heard of is called out in red rather than left to look like somebody with no pull requests. A typo returns nothing, which on screen is indistinguishable from a quiet week, and one of those is a fact about a person while the other is a fact about a config line.

#Where people are stuck

A block per person, led by what is in their way, sorted by how much is stuck rather than alphabetically or by volume. The name at the top is the one to ask about. The cards are the board's own, with the same colours and chips, minus the pin, note and snooze, which are statements about work you are going to do yourself. Signals you have switched off apply here too.

#Waiting on review

The team's own pull requests that nobody has got to, oldest first. Built from what the team wrote rather than what it has been asked to review: a review the team owes somebody else is their problem, a review the team is owed is work of theirs that is not moving. Approved and draft ones are left out, since an approved pull request is waiting on its author.

Who it is waiting on reads as whoever was asked, teams included, since routing a review to a group is a real answer. Where nobody is pending there are two opposite situations and the row says which: nobody asked means no reviewer was ever requested, while reviewed, nobody waiting means somebody was asked, answered, and it is back with the author. GitHub drops a request the moment that person submits a review, so these look identical in the data and only one of them wants a reviewer found.

Colour runs opposite to the board here, on purpose. A card goes grey in Your work once it is stale, because the board has decided you cannot act on it. A review that has waited five months is the reverse: the longer it sits, the more it is somebody's job to unstick it. Over three weeks is red, over one is amber.

#Tickets you raised

Where the things you asked for ended up. Jira has no assigner: nothing records who handed a ticket to somebody, and the assignee field keeps no history of how it got its value, so this goes on reporter, which for work given out is usually the same person.

Not filtered to other people's names, deliberately. A ticket you raised and never gave anybody is the one most likely to have been forgotten, precisely because it is your own doing and nothing else on the board mentions it. Those come first, in red. Then whoever holds it, then your own last, since they are already on your board under My tickets and would otherwise bury the rest.

#What it costs

About what one person costs. Jira takes an assignee in (...) clause and GitHub ORs repeated author: terms in one search, so the queries do not multiply by the size of the team. It is fetched on the first switch and cached, so a board nobody switches pays nothing.

What does not scale is the answer. Both queries take a maximum and both order by recency, so a team large enough to exceed one would lose whoever has been quiet longest, which on screen is a person reported as having nothing on. A result that comes back exactly full is reported as incomplete instead.

Other people's tickets raise fewer signals than your own. The search cannot return updated, as described under Connecting Jira, and the detail pass that would fill it in costs about a second per ticket. So the age-based rules stay quiet for team members rather than reporting a wrong number. Everything that comes from GitHub is unaffected, which is where most of being stuck lives.

#What leaves your machine

The server talks to GitHub, to Jira, to the public status pages you have chosen, and to Wikipedia for the loading strip. That is the whole list. There is no telemetry, no analytics and no account.

Credentials are read from gh or from your own .env, and are never written anywhere by this project. The setup panel collects nothing: a token typed into a web field is worse off than one in a file, so credentials are named, their file is pointed at, and that is all. Each check reports where a credential came from and whether it worked, never the credential itself.

Your pins, notes, filters, critical flags and theme live in localStorage in your own browser.

#Troubleshooting

Start with Check setup in Settings. It names each source, says whether it is working and gives you the command to fix it.

SymptomUsually
Jira is missing entirely Not signed in. The banner says so and offers a Sign in button; acli jira auth login --web does the same from a terminal
Signing in opened a browser, you approved, and nothing happened Fixed in 1.4.1. acli draws a terminal picker after the callback lands and waits for Enter, which nothing could press. Older copies sit there until they time out. Update, or finish that one in a terminal
Tickets appear, but with no times, epics or comments Normal for a second or two. Those come from a per-ticket pass that runs behind the first paint. If they never arrive, check acli jira auth status
Tickets with open PRs never flag as out of sync None of your in-progress statuses is recognised as review. Set JIRA_REVIEW_STATUSES
No On hold section Your parked status is named something the defaults do not cover. Set JIRA_PARKED_STATUSES
Pull requests missing, or zero reviews The token is not being found. Check gh auth status, and remember a launcher with a minimal PATH may not find gh at all
The calendar shows a meeting that was cancelled or moved The snapshot is older than the change. It refreshes in the background every ten minutes, and the sync after the change marks the meeting rather than quietly dropping it
The calendar strip claims a free day The snapshot is from another day. It says it is out of date rather than guessing, and asks for a fresh one
Edits to the code change nothing The server reads its modules once at boot. The banner says which version is running against which is installed, with a Restart button where something is supervising the process to bring it back
Somebody on the team shows no pull requests Usually their GitHub handle in TEAM. A handle that does not exist is called out in red beside their name; one that exists but belongs to somebody else is not something this can detect
